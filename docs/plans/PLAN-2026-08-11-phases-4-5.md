# PLAN — Phases 4 and 5: the pipeline moves, and a gate disappears

Continues `PLAN-2026-08-08-self-improving-pipeline.md`. Phases 1–3 are done.
These two are the ones that plan calls decisions rather than repairs: phase 4 is
the first point where the pipeline moves unattended, phase 5 the first where a
gate stops asking.

Both are now possible for one reason: the holdout×3 baseline was completed on
2026-08-11 — 75 of 75 evals, three samples each, majority judge. Until today
every "conclusively passes" claim rested on single draws.

## What the evidence actually says

Of 75 evals at holdout×3:

| Interval verdict | Count |
|---|---|
| passed — interval entirely above the bar | 30 |
| inconclusive — interval spans the bar | 32 |
| failed — interval entirely below | 13 |

Thirty is not the answer, though. Two of the plan's own limits cut into it, and
both are mechanical rather than judgement:

- **`sharedExpanded` non-empty** means the harness inlined `_shared` contracts
  into the actor's prompt. The agent was handed something it may never fetch on
  a live run — and on 2026-08-07 architect did not fetch the one whose command
  sat verbatim in its own file. Nineteen of the thirty have an empty list.
- **`actorSource` must be `agent:<name>`.** One of the thirty ran against the
  generic actor, which measures the eval, not the agent.

## Phase 5 — gate tiering by proof

A gate drops to notify-only when ALL of:

1. `power.status === 'passed'` at holdout×3 — the interval, never the point
2. `sharedExpanded` empty — the eval exercised the handoff, not a fixture
3. `actorSource` starts with `agent:` — the real prompt was under test
4. the agent is not Class A

Class A is not configuration. `devops` and `infra-provisioner` both clear (1)
today — devops at 82% [72%, 89%] — and both stay gated, because the question at
a production deploy is not competence (ADR-009). A tier computed from evidence
that cannot refuse those two is not a tier, it is a rubber stamp.

`notify-only` means: the pipeline proceeds, the entry still appears in the
board's inbox, the human may intervene and need not.

**Deliverable:** `scripts/lib/gate-tier.mjs` — pure, tested, with a CLI that
prints who qualifies and, for everyone else, the specific reason. The reason
matters more than the verdict: "inconclusive" and "fixture-inlined" are
different work.

## Phase 4 — gate:prompt and holdout rotation

The loop's steps 4–6:

```
4. Tuning improves → run HOLDOUT once. The improver sees the NUMBER, never the failures.
5. Holdout improves conclusively → raise gate:prompt for a human.
6. Approved → the prompt lands, and the holdout ROTATES.
```

**Rotation is the part that is easy to skip and expensive to skip.** A holdout
read enough times stops being one, even through the number alone: each
comparison leaks a bit, and after enough rounds the improver has fitted the
holdout through the only channel it has. So an approved prompt costs a rotation.

Rotation must be deterministic and recorded, or it becomes a way to reshuffle
until the number is favourable. The seed is the approved prompt's own hash, and
the move is written to the eval file so a reader can see which cases moved and
when.

**Deliverables:**
- `scripts/lib/holdout-rotation.mjs` — `rotate(cases, {seed, fraction})`,
  deterministic, recorded, reversible.
- `gate:prompt` raised by the improver when and only when holdout improved
  conclusively; the human approves, and only then does the prompt land.

## What neither phase does

Unchanged from the parent plan, restated because this is where they would be
quietly dropped:

- No gate is removed on anything expensive to undo, at any score.
- No agent edits its own prompt unattended. `gate:prompt` is a human.
- No point estimate is a result. Every "improves" is the interval.
