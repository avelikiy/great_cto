# ADR-035: Fast feedback and source-bound final verification

**Status:** Proposed implementation; not merge, release or installation approval.
**Date:** 2026-10-18
Tracking: great_cto-o1ul. Related: [trusted local checks](ADR-trusted-local-checks.md).

## Context

A recorded serial run spent 316488 ms in root/hooks/board and 1339561 ms in
libraries. These two stages alone took 27.6 minutes. Focused tests, canonical
verification, independent review and delivered-runtime acceptance answer
different questions. Running a complete gate during each edit is expensive;
editing the candidate during it invalidates a final-source claim.

## Decision

`scripts/verify.mjs` offers two explicit modes, both requiring a Git base.
Feedback reuses the existing affected-test mapper, including committed changes
against the merge base, dirty changes and untracked paths. Docs select existing
doc checks; board changes select board tests, browser E2E and rendered contrast;
runtime changes select mapped Node tests. Security/policy/config changes,
unsupported runners, deletions without runnable coverage and partial mappings
explicitly require the full gate. Feedback executes fixed argv, never the
mapper's human-readable shell strings. CLI output is rebuilt before tests.

Final mode requires clean tracked and untracked state, then executes the entire
unchanged `ci-local.sh --e2e` inventory. No selective final gate or cached pass is
introduced. Browser preflight performs an actual launch before expensive work;
it never downloads, prunes caches or starts models. An unavailable prerequisite
blocks the run. Final postflight repeats the browser check.

Auto scheduling chooses one or two workers using available CPU, available memory
and load. macOS uses the read-only system memory-pressure query, Linux uses
MemAvailable; missing measurements conservatively fall back to free memory.
Explicit one/two-worker choices remain possible. This is a scheduling
heuristic, not a performance guarantee. Test deadlines and assertions do not
change. Timings and logs are retained per run for measurement.

## Evidence and invalidation

Final receipts bind HEAD, tree and canonical-script hash. Directory watchers
and tracked-file inode/size/mtime/ctime snapshots invalidate source edits even
when the bytes are subsequently restored; metadata covers delayed macOS events.
New nonignored paths, watcher failures and final snapshot differences refuse
final-source evidence. Ignored build output remains permitted. Source events
are checked again after browser postflight. Receipts retain skipped counts and
distinguish passed, passed-with-not-checked, failed, blocked, unknown and
invalidated outcomes. A missing canonical completion footer is unknown.

`--check-receipt` checks current clean source identity only. Local JSON is not a
signature, trusted attestation or authorization. Every receipt has
`mergeEligible: false`; independent review and existing merge/release approval
remain external requirements. Installed dependencies, ignored generated bytes,
arbitrary external inputs and descendant quiescence are not fully attested.
Filesystem watchers do not establish hostile-filesystem or remote-builder trust.

## Alternatives and consequences

Always running the full suite provides broad coverage but delays feedback.
Selective-only final gates could miss cross-component regressions and are not
adopted. Increasing worker counts without process isolation risks flakes, so
the first bound remains two. Whole-environment immutable builds would provide
stronger provenance but are a separate sandbox/toolchain project.

The 1–3 minute feedback budget is a target, not a benchmark result. Measure
actual durations, full reruns, regressions and rework before making speed or
quality claims. No domain agents, mandatory review roles or human approval
requirements are removed. This is repo tooling; the installed plugins and
operator board are not modified by running a plan or preflight.
