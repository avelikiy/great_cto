# ADR-034: Focused presentation without specialist removal

**Status:** Proposed; local candidate, not release or default execution approval.
**Date:** 2026-10-16
Tracking: great_cto-e76b, great_cto-v53m, great_cto-e76b.1.
Related: [domain foundation](ADR-032-domain-evidence-pilot.md),
[host admission](ADR-033-explicit-domain-host-admission.md).

## Context

A large installed catalog is not evidence of expertise or a useful execution
plan. Five domain candidates exist, but matched native quality trials have not
run. Public claims must distinguish preparation, invocation and measured outcome.

## Decision

Fleet defaults to Project focus: eight existing core role identifiers plus the
selected project's required reviewers. This is a display projection, not a
change to dispatch, role files, permissions or required-reviewer enforcement.
Needs attention and All agents retain catalog-wide scope. Required retired roles
remain visible in focus; missing installations are named explicitly. Unknown
requirements fall back to the installed catalog with an English status message.
Request generation and project scope fence reviewer and roster replies.

The focus control uses the existing sidebar pattern, keyboard Enter/Space,
aria-pressed state and a status region. No new colors, spacing or CSS tokens.
Project focus, unknown-policy fallback, full catalog and attention views are
separate states; loading is never interpreted as an empty mandatory reviewer set.

No industry reviewer is deleted. Eight available core roles do not mean eight
mandatory model calls. Task-dependent specialist admission remains existing policy.
Five packs remain candidates; mental wellbeing safety is not clinical efficacy.

## Alternatives

Deleting other roles risks compatibility and removal of preventive checks.
Filtering by role-name keywords would conflate industries with jurisdictions.
Keeping the entire roster as the default obscures project requirements. A
reversible presentation projection avoids all three.

## Experiment boundary

`node scripts/domain-benchmark.mjs plan` prints an anonymous design with three
task proposals, two hosts, two arms and three repetitions: 36 unexecuted slots.
It is not preregistration. Source, holdout, scorer, model, policy and budget pins
remain null until actually frozen. The existing preregister command rejects
this design as input. There is no second executor, scan, scorer or model call.
Private project mappings and overlays stay outside this public document.

Launch requires reviewed executable hidden checks, independent scorer, pinned
models/policies, verified isolation/receipts, per-trial and aggregate spend caps
and explicit launch approval. Three task clusters are an exploratory pilot;
repetitions do not create independent projects or establish broad expertise.
Acceptance, serious regressions, rework, human corrections and full cost per
accepted task remain Unknown until actual observations exist.

## Consequences

The UI is smaller when project policy is known, not necessarily eight rows.
The full catalog and all existing enforcement remain available. A failed policy
read deliberately restores noise rather than falsely implying irrelevance.
Expertise positioning and active-call reduction require separate outcome evidence.
Implementation work is tracked in Beads; merge, release and local activation
remain separate decisions after verification and independent review.

## Verification

Pure page tests cover core/required membership, retired required roles, unknown
policy and stale responses. Chromium exercises focus, keyboard navigation,
catalog restoration and unknown-policy fallback. Existing domain protocol tests
must remain green. Plan checks cover all 36 unique slots, counterbalanced order,
null metrics/pins and refusal to preregister an unfrozen design.
