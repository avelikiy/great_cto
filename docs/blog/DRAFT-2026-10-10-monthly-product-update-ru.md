# Два хоста, один процесс: как изменился great_cto за месяц

Когда над задачей работают несколько AI-агентов, сложнее всего не получить код. Сложнее понять, кто его изменил, что проверил следующий агент и можно ли продолжать после остановки. Если добавить вторую экосистему, вопросов становится больше: кто управляет очередностью, как передаются результаты и что происходит, когда один хост завершился, а другой нет?

За последний месяц мы сосредоточились именно на этих вопросах. great_cto получил управляемый путь исполнения в Codex, маршрутизацию ролей между Codex и Claude Code, более строгие проверки результатов и заметно переработанную локальную админку.

Этот обзор охватывает изменения с 10 сентября по 10 октября 2026 года. Последняя опубликованная версия на момент обновления статьи: **3.62.0**, доступна в GitHub Releases и npm. Архив из registry совпал с проверенным релизным архивом; отдельная consumer-установка подтвердила CLI и автономную админку. Локальные Claude Code, Codex и терминальный CLI обновлены до этой версии. Админка оператора подтвердила ту же версию через API. При запуске были пятисекундные таймауты; позже API и HTML восстановились без повторного рестарта. Проблему отзывчивости на реальных проектах не считаем исправленной: восстановление ответа не доказывает устойчивость.

## Архитектура: управление прогоном стало явным

great_cto уже умел проводить задачу через продуктовую проработку, архитектуру, реализацию и ревью. За месяц появился отдельный контролируемый runtime для Codex, а затем возможность подключать к тому же прогону Claude Code.

В этом режиме модель не определяет сама, какие стадии можно пропустить. Контроллер читает граф pipeline, выбирает роль, сохраняет попытку выполнения и проверяет результат перед переходом дальше.

Упрощённо цикл выглядит так:

```text
Задача и критерии приёмки
          ↓
Роль и назначенный ей хост
          ↓
Предложенные изменения → проверка допустимости → запись файлов
          ↓
Проверки и отдельный verifier
          ↓
Следующая стадия / доработка / остановка / решение человека
```

Важная деталь: в контролируемом режиме worker предлагает изменения файлов, а записывает их контроллер. До записи проверяются разрешённые пути, защищённые файлы, симлинки, размер и соответствие исходному содержимому. Затем отдельная read-only сессия verifier смотрит на фактические файлы, а не только на отчёт исполнителя.

Состояние прогона хранится вне рабочего пространства worker. У попыток есть идентификаторы, результаты проверки и данные о входных артефактах. Одобрение связано с конкретным состоянием: если артефакты изменились, старое решение больше не разрешает продолжение.

Это не универсальная защита от любого процесса на компьютере. Контроллер доверяет локальному оператору и ограничениям хоста. Его задача конкретнее: не дать обычному сбою, устаревшему approval или некорректному ответу модели незаметно превратиться в успешную стадию. [Контракт управляемого runtime](https://github.com/avelikiy/great_cto/blob/v3.59.1/docs/HOST-CODEX.md).

### Claude Code и Codex могут участвовать в одном прогоне

В версии 3.47.0 появилась маршрутизация по ролям. Например, QA можно поручить Claude Code, а security review оставить Codex.

Совместная работа не означает, что два агента одновременно переписывают одну рабочую копию. Независимые роли ревью получают один зафиксированный снимок кода и могут работать параллельно. Контроллер проверяет их предложения на пересечение путей, применяет допустимые результаты последовательно и сохраняет проверки и человеческие gates. Изменения реализации идут в порядке зависимостей.

Карта маршрутов фиксируется при старте. Оба CLI должны быть установлены и авторизованы; отсутствие доступного хоста не выдаётся за завершённое ревью. Прерванную волну нельзя просто незаметно запустить второй раз. [Релиз смешанной маршрутизации](https://github.com/avelikiy/great_cto/releases/tag/v3.47.0).

При этом два режима остаются разными. В Claude Code есть нативный workflow плагина. В Codex pipeline запускается через CLI-контроллер; обычная сессия Codex получает plugin hooks, skills и MCP, но не становится управляемым прогоном автоматически. Симметричный процесс не требует притворяться, что интерфейсы хостов одинаковы.

### Передача контекста стала наблюдаемой

Следующая стадия должна знать не всю историю разговора, а релевантные результаты предыдущих стадий. Теперь контролируемый runtime сохраняет отдельный context packet и записывает, какие результаты были переданы, сколько места они занимают и что пришлось сократить.

Для пакета установлен бюджет 64 KiB. При переполнении старые результаты механически сокращаются, а сокращённые роли явно перечисляются. Перед запуском проверяется хеш файла. Это позволяет расследовать не только «что агент сделал», но и «какие данные он получил». [ADR-026](https://github.com/avelikiy/great_cto/blob/v3.59.1/docs/adr/ADR-026-stage-context-packet.md).

Для нативного архитектурного workflow появилась отдельная opt-in возможность: council независимых черновиков. Другие модели проектируют решение из одинаковых входных данных, не читая черновики друг друга. Architect собирает итоговый документ и выносит расхождения на обсуждение. Совпадение ответов не объявляется доказательством правильности; недоступный участник обозначается как недоступный. Совет включается на уровне проекта и не добавляет платные вызовы всем пользователям по умолчанию. [ADR-025](https://github.com/avelikiy/great_cto/blob/v3.59.1/docs/adr/ADR-025-council-architecture-drafts.md).

## Функционал: меньше команд, больше определённости

В сентябре мы сократили поверхность команд с 43 до 21, объединив пересекающиеся операции. В октябре выделили три ежедневных действия:

```text
Claude Code:  /start    /inbox    /resume
Терминал:    run       status    resume
```

Для контролируемого Codex-пути команда выглядит так:

```bash
great-cto run "Add CSV export" --host codex --allow src,tests,docs
```

`status` позволяет увидеть состояние без нового вызова модели. `resume` продолжает работу, но сам по себе не одобряет pending gate и не расширяет разрешённую область изменений.

Управляемые задачи получили общую идентичность, цель, критерии приёмки и явные связи с run/session. Project lease защищает от конкурирующих управляемых запусков в одном проекте. Это общий слой учёта задач, а не разрешение любым независимым сессиям одновременно менять репозиторий. [Релиз общего слоя задач](https://github.com/avelikiy/great_cto/releases/tag/v3.48.0).

### «Проверено» теперь требует более конкретных оснований

За месяц усилились условия `gate:ship`. Для соответствующих проектов доменные reviewers стали обязательными. Открытые негативные findings и устаревшие QA/security verdicts могут блокировать выпуск. Старый отчёт о другом состоянии кода больше не должен выглядеть как актуальное разрешение на релиз.

Проверяется и качество самих свидетельств: цитата в finding должна находиться в указанном файле. У агентов появились eval-наборы под их собственные роли; пустой или обрезанный ответ исполнителя отделяется от содержательной неудачи. Наличие набора evals ещё не означает, что все модели прошли свежий live-прогон. Эти изменения отражены в [changelog выпущенной версии](https://github.com/avelikiy/great_cto/blob/v3.59.1/CHANGELOG.md).

Codex получил шесть safety guards через plugin hooks. Добавились защита общей рабочей копии от разрушительных Git-операций и подсказки о влиянии правки. Для нативных сессий появились локальные снимки изменений по ходам агента, доступные в админке. Такие снимки не отправляются обычным push.

Для write-requiring проверок контролируемого runtime доступны offline Docker executor и явно разрешённый trusted-local backend. Policy задаёт оператор: образ или локальный режим, входные файлы, команды и ограничения. Локальный backend предназначен для доверенного кода и не даёт изоляции контейнера. Docker не стал обязательной зависимостью всего продукта. Если executor не запускался, это означает отсутствие этой проверки, а не её успешное прохождение.

### Новый специалист для смарт-контрактов

В roster теперь 72 агента. Новый аудитор смарт-контрактов дополняет проектный threat modeling анализом уже написанных контрактов.

Его контракт требует использовать доступные инструменты, например Slither, Aderyn, Solhint и Foundry, проверять достижимость findings и давать PoC для Critical/High. Инструмент, который не удалось запустить, обозначается как `not checked`. Добавился и режим подготовки пакета для внешнего аудита.

Это инженерный workflow, а не сертификат безопасности. В DeFi особенно важно не путать отсутствие найденной проблемы с доказанным отсутствием проблемы. [Релиз аудитора](https://github.com/avelikiy/great_cto/releases/tag/v3.49.0), [пакет для внешнего аудита](https://github.com/avelikiy/great_cto/releases/tag/v3.51.0).

## Админка: от списка агентов к рабочему пульту

Локальная админка теперь открывается на Work. В центре внимания задачи и решения, которые ждут человека. Инструменты диагностики остаются рядом, но не подменяют основной сценарий работы.

Навигацию привели к одному стилю: одинаковые размеры строк, состояния выбора, hover/focus и иконки. Tools больше не прижат к нижнему краю отдельно от остальных пунктов. Обновлены поведение project switcher и фильтрация списка при вводе.

Самое содержательное изменение: **task cockpit**. В одном месте видны стадия, критерии приёмки, записанные evidence, blockers и ограниченная история связанной активности. Он читает существующие task/controller stores и не создаёт второго управляющего контура. Это не интерактивный терминал: произвольный ввод в работающего агента здесь не реализован.

Другие экраны помогают ответить на более узкие вопросы:

- **Decisions:** что ждёт решения и какая сессия остановилась на запросе разрешения.
- **History и Turns:** что происходило и какие файлы изменились на конкретном ходе.
- **Fleet:** кого действительно вызывали и какие обязательные reviewers ещё не оставили verdict.
- **Harness:** состояние управляемых прогонов.
- **Usage:** потребление Claude Code и Codex, относимое к выбранному проекту, из локальной истории хостов.
- **Skills:** read-only inventory локальных документов для Claude Code, Codex, общих каталогов и registry.

В Usage появились периоды 7/30/90 дней, дневная динамика токенов, тяжёлые conversations, модели, инструменты, агенты и cache usage. Чтение учитывает особенности форматов хостов: например, повторяющиеся usage-поля одного ответа Claude не должны многократно увеличивать расход.

В 3.60.0 статистика ограничена выбранным проектом, включая существующие связанные Git worktrees. Разговор с похожим названием не становится его расходом: важна восстановленная идентичность проекта. История без такой идентичности исключается, и экран прямо предупреждает об этом. Общие лимиты подписки не выдаются за проектную статистику. Отсутствие относимых записей не доказывает, что работы не было.

Интерфейс получил единое английское форматирование чисел, дат и времени. Это не перевод пользовательского контента: описания задач и документы остаются на исходном языке.

Новый экран Skills показывает местоположение документа, scope, SHA-256 его содержимого и структурные предупреждения. Наличие файла не означает, что хост включил или загрузил skill. Хеш не покрывает его scripts и references, а происхождение upstream и качество выполнения задачи здесь не измеряются. Если чтение неполное или достигнут лимит сканирования, inventory обозначается как partial, не как полный успешный аудит. Экран ничего не устанавливает и не исполняет. [Релиз 3.60.0](https://github.com/avelikiy/great_cto/releases/tag/v3.60.0), [контракт inventory](https://github.com/avelikiy/great_cto/blob/v3.60.0/docs/adr/ADR-029-read-only-skill-inventory.md).

Долларовые значения здесь обозначают API list-price equivalent, а не фактический счёт за подписку. Неизвестная цена отображается как `n/a`. Данные о лимитах Claude доступны через отдельно включаемый statusline recorder; отсутствие записи не превращается в выдуманный процент.

Тяжёлое чтение Usage вынесено в ограниченный background worker. Пока идёт обновление, экран может использовать кэш. Это устраняет конкретную причину блокировки HTTP-обработки, но не означает, что все источники задержек админки уже закрыты. Индексация истории Usage локальная, без отправки usage telemetry. [Usage](https://github.com/avelikiy/great_cto/releases/tag/v3.53.0), [обновлённая админка](https://github.com/avelikiy/great_cto/releases/tag/v3.59.0).

После установки 3.61.0 повторная live-проверка поймала таймауты даже у служебного `/api/version`. Перезапуск временно восстановил быстрые ответы, затем зависание повторилось. Диагностический trace выявил один блокирующий путь: сбор inbox по другим проектам вызывает синхронный `bd list`. Один такой вызов занял 19,38 секунды в main thread. Это открытый P1 bug: причина одного медленного пути найдена, постоянное исправление ещё не выпущено. [Наблюдение и восстановление](https://github.com/avelikiy/great_cto/blob/main/docs/qa-reports/QA-2026-10-10-updater-release.md).

### Из проверенной задачи можно подготовить draft PR

Для управляемой verified-задачи добавлен путь публикации из чистой, закоммиченной feature branch. Сначала preview, затем явное подтверждение. Проверяются scope, verification receipt, состояние Git и история отправляемых изменений, а не только итоговый diff.

Это ещё не «одна кнопка до production». Draft PR не разрешает merge, release или deploy. Автокоммит грязной рабочей копии не поддерживается. Новый путь покрыт автоматическими проверками с локальными Git remotes и mocked GitHub; live-проверка публикации в GitHub для него пока не подтверждена. [ADR-028](https://github.com/avelikiy/great_cto/blob/v3.59.1/docs/adr/ADR-028-task-cockpit.md).

В 3.59.1 исправили и установочный слой: админка из Git-installed plugin больше не зависит от отсутствующей CLI-сборки для расчёта gate policy. Поведение policy сверяется с CLI, а installer tests не запускают лишнюю фоновую админку. [Исправление runtime](https://github.com/avelikiy/great_cto/releases/tag/v3.59.1).

Для 3.60.0 проверили не только исходную ветку, но и доставленный npm-пакет: архив сверили по integrity, установили в отдельный consumer prefix и проверили автономную админку, Skills и проектную изоляцию статистики обоих хостов. Полный локальный gate включает 14 реальных браузерных сценариев, все они прошли. Четыре opt-in live-сценария остались not checked; дополнительный устаревший pytest-набор отсутствует и отмечен отдельно. Это не доказательство нового live-прогона моделей или полного цикла до production. [QA релиза](https://github.com/avelikiy/great_cto/blob/main/docs/qa-reports/QA-2026-10-10-skills-release.md).

## Стало ли качество выше?

Появился сравнительный benchmark для трёх вариантов: Codex-only, Claude-only и mixed. Для каждого варианта используются одинаковая спецификация, одинаковое число вызовов и одинаковый лимит времени на вызов. Скрытые проверки evaluator не передаются исполнителям.

В завершённом повторном исследовании на двух синтетических задачах каждый вариант прошёл **24 из 24 финальных проверок**. Наблюдаемый прирост mixed относительно обеих базовых конфигураций: **0 процентных пунктов**.

Это не доказывает, что две экосистемы всегда равны одной. Уже первые решения достигли потолка этого маленького набора задач. Результат не позволяет заявить ни общий процент роста качества продукта, ни выигрыш по стоимости, ни надёжность полного цикла до production. Неудачные предыдущие попытки сохранены отдельно, а не заменены успешным повтором. [Отчёт исследования](https://github.com/avelikiy/great_cto/blob/v3.59.1/docs/analysis/2026-10-02-host-quality-recheck.md).

Что изменилось уже сейчас: стало больше механизмов, которые делают результат проверяемым, а сбой видимым. Насколько это улучшает продукт на сложных задачах, должен показать более широкий benchmark, а не количество агентов или красивый dashboard.

### Codex-плагин получил опциональное автообновление

В 3.61.0 появился macOS updater: после явного включения он вызывает штатное обновление Git marketplace при загрузке задания и затем каждые шесть часов. Перед каждым refresh проверяется origin: неожиданная смена репозитория останавливает обновление. Файлы кеша заменяет Codex, не сам helper.

Это отдельный механизм для Codex-плагина, а не автообновление npm CLI. Он следует настроенному Git ref marketplace, по умолчанию `main`, который может опережать npm-релиз. Helper нужно держать по стабильному пути; новые hooks по-прежнему требуют review хоста. `status` подтверждает расписание, но не успешную установку.

После выпуска первый запуск нового задания завершился с exit 0 и обновлённым marketplace в отчёте. Установленный Codex подтвердил 3.61.0. Установка остальных локальных компонентов тоже выполняла refresh Codex, поэтому переход версии не приписываем исключительно таймеру. Повторный шестичасовой запуск ещё не наблюдали. При установке обнаружили старое загруженное задание без plist: его миграцию восстановили локально, а автоматическую обработку такого случая оставили отдельным bug. [Релиз 3.61.0](https://github.com/avelikiy/great_cto/releases/tag/v3.61.0), [QA доставки](https://github.com/avelikiy/great_cto/blob/main/docs/qa-reports/QA-2026-10-10-updater-release.md).

## Адаптивный pipeline: меньше остановок, но не меньше обязательных проверок

PR [#173](https://github.com/avelikiy/great_cto/pull/173), [#175](https://github.com/avelikiy/great_cto/pull/175) и [#176](https://github.com/avelikiy/great_cto/pull/176) выпущены в 3.60.0, [#163](https://github.com/avelikiy/great_cto/pull/163) в 3.61.0. Адаптивный pipeline из [#167](https://github.com/avelikiy/great_cto/pull/167) вошёл в [GitHub Release 3.62.0](https://github.com/avelikiy/great_cto/releases/tag/v3.62.0). Все пять PR теперь merged.

Новый режим включается явно. Он выбирает глубину процесса, но сохраняет обязательный минимум проверок для риска проекта. Артефакты и решения привязаны к снимку Git: изменение входных данных делает прежнее разрешение устаревшим. Defaults существующих проектов не меняются.

Появился общий операторский бюджет для локальных Claude Code и контролируемых Codex workers/verifiers. Резервирование выполняется целиком, а не частично; ограничения защищены от конкурирующих участников. Это не общий биллинг провайдеров и не распределённая гарантия для независимых машин.

Проверки специалистов разделены по фазам. Историческое evidence можно использовать только в допустимой области и после свежей независимой проверки полноты. Основные code review, QA, security и AI evals не заменяются повторным использованием старых verdicts.

Независимое ревью нашло и помогло закрыть P1: диагностические команды Git могли запускать настроенные проектом вспомогательные программы до допуска worker в sandbox. Эти чтения переведены на ограниченный read-only helper. Финальный полный локальный gate снимка `8542e41e` завершился без ошибок: 3320 библиотечных проверок, 1360 root/hooks/board, 14 браузерных сценариев и 36 candidate pipeline-проверок прошли. Числа разных suites пересекаются, складывать их в число уникальных тестов нельзя. **15 сценариев остались not checked**, включая opt-in live-сценарии и непроверенные внешние действия.

Ранее красные прогоны сохранены. В частности, сценарии abrupt owner/scorer death теперь честно характеризуют ограниченный результат, а не обещают ещё не реализованный независимый teardown. Строгие проверки graceful-unwind после смерти helper, обычного завершения, отказа и TERM сохранены и прошли финальный gate. Исходная причина прежнего helper failure остаётся Unknown. Production guardian не активирован, дополнительные права OS cleanup не выданы. Независимый reviewer одобрил выпуск только в этой экспериментальной opt-in области. Это не подтверждение полного live-цикла до production. [Детали ревью и проверок](https://github.com/avelikiy/great_cto/blob/main/docs/qa-reports/QA-2026-10-10-adaptive-independent-review.md).

## Итог

За месяц great_cto стал лучше отвечать на три вопроса: кто сейчас работает над задачей, на каком основании работа считается проверенной и что именно должен решить человек.

Claude Code и Codex могут участвовать в одном управляемом процессе. Контроллер сохраняет порядок стадий, ограничивает изменения и связывает решения с проверенными артефактами. Админка показывает этот процесс ближе к задаче, а не заставляет собирать его из разрозненных списков агентов.

Дальше важнее не расширять roster ради числа. Важнее устранить блокирующее чтение Beads в админке, проверить live-пути адаптивного режима и устойчивость автообновления, а затем измерить качество на задачах, которые действительно различают конфигурации. Сильный pipeline должен не только работать. Он должен позволять понять, почему его результат заслуживает доверия.
